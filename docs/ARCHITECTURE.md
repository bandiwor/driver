# Архитектура Kuzov

Kuzov — браузерная песочница вождения с мягкой (node–beam) физикой кузова,
процедурными моделями машин и процедурным звуком. Проект оригинальный: жанр
«soft-body driving sandbox» и общеизвестная техника масс-пружинных сеток, но
собственные машины, звук, UI, иконки и визуальный стиль — без чужих ассетов,
названий и брендинга.

## 1. Принципы

1. **Ядро не знает о браузере.** `core/`, `physics/`, `vehicles/`, `input/`,
   `audio/dsp/` — чистый TypeScript без DOM и three.js. Они запускаются в Node
   (Vitest), в snapshot-режиме и (позже) в Web Worker.
2. **Данные, а не классы.** Мягкое тело — плоские typed arrays (SoA). Машина —
   объект `VehicleDef`. Параметры тюнинга — схема `ParamDef[]`. Отсюда
   генерируются физика, меш, звук и UI.
3. **Всё — плагин.** `Kernel` собирает игру из плагинов, которые регистрируют
   сервисы (типизированные токены) и системы (упорядоченные апдейты). Любую
   часть можно заменить или выключить: в тестах нет рендера, в снапшотах нет
   ввода и звука.
4. **Детерминизм.** Фиксированный шаг, инъекция часов/планировщика, свой PRNG.
   Одинаковые входы → побитово одинаковый результат (есть тест).
5. **Ноль аллокаций в горячем цикле.** Солвер, синтез звука, обновление меша —
   без `new` и замыканий на кадр. Временные объекты — модульные константы.
6. **Каждый модуль можно проверить отдельно:** unit-тестом, perf-тестом или
   скриншотом из любой проекции.

(`import/no-cycle`).

## 3. Кадр и время

Физика по умолчанию живёт в **Web Worker** со своими часами; главный поток
только рисует и читает готовые состояния.

```
Physics worker (SimServer)                    Main thread
──────────────────────────                    ───────────
loop: accumulator по wallMs                   rAF ─► FixedStepLoop (120 Гц)
  while acc ≥ 1/120 (≤ 8):                      fixed:  0  input   — педали/руль, команды
    controls ← SAB (последние)                          20 sim     — controls → SAB (inline: шаг)
    Simulation.step():                          frame:  0  input   — UI-действия (и на паузе)
      vehicle.pre (двигатель, КПП)                      5  sim.sync — снапшот → shadow-машина, alpha
      PhysicsWorld: 16 сабшагов ≈ 1920 Гц               40 audio
      vehicle.post (BodyFrame)                          50 camera
  снапшот → тройной буфер (SAB)  ──────────►            60 render  — prevPos→pos по alpha
  Atomics.wait(до следующего шага)                      90 telemetry
  yield через MessageChannel                  UI: 15 Гц Telemetry → signals
```

* **Игровой шаг 120 Гц**, **солвер ≈ 2 кГц** (сабшаги). Явная схема
  (semi-implicit Euler) стабильна при жёстких балках (k ≈ 10⁶ Н/м) только на
  таком шаге.
* **Рендер интерполирует** между двумя последними физическими состояниями
  (в снапшоте есть и `pos`, и `prevPos`). В worker-режиме
  `alpha = (now − t_снапшота) / dt` — картинка показывается на один шаг позади,
  поэтому плавность не зависит ни от частоты монитора, ни от джиттера потоков.
* Если рендер тормозит (тяжёлая сцена, слабая GPU), физика продолжает идти
  ровно 120 шагов/с — управление и звук не «плывут».
* `loop.simulate(seconds)` — синхронная прокрутка для тестов и снапшотов
  (там всегда inline).

## 4. Физика

### 4.1 Мягкое тело (`physics/softbody`)

| Массив | Размер | Смысл |
|---|---|---|
| `pos`, `vel`, `force` | 3·N, f64 | узлы |
| `invMass`, `nodeFriction` | N | |
| `beamA`, `beamB` | M, u32 | балки |
| `rest`, `rest0` | M, f64 | текущая (пластически изменённая) и исходная длина |
| `spring`, `damp` | M | Н/м, Н·с/м |
| `yieldStrain`, `breakStrain` | M | порог пластики и разрыва |
| `flags` | M, u8 | `Broken`, `CompressionOnly` |

Сабшаг: силы балок (пружина + демпфер вдоль оси) → пластика (rest «течёт»,
удерживая упругую деформацию на пороге yield) → разрыв по полной деформации
относительно `rest0` → интегрирование → контакт с землёй (проекция,
restitution, кулоново трение). Аллокаций нет.

`SoftBodyBuilder` собирает тело (дедупликация балок), `buildLattice` строит
каркас кузова из поперечных сечений (`BodyStation`), `buildVehicleBody`
добавляет точки колёс. `BodyFrame` — «жёсткая» система координат деформируемого
тела (центр масс + оси из групп опорных узлов): её используют камеры, колёса,
HUD.

Оси машины: **+x — влево, +y — вверх, +z — вперёд** (правая тройка three.js).

### 4.2 Трансмиссия и шины (`physics/vehicle`)

Чистые функции + struct-состояние: `engine.ts` (карта момента, потери,
насосное торможение, холостой регулятор, отсечка с гистерезисом),
`gearbox.ts` (передачи, главная пара, сцепление как насыщаемая муфта, автомат),
`tyre.ts` (Magic Formula + эллипс трения), `curve.ts` (кусочно-линейные карты).

### 4.3 Шасси: колёса, подвеска, привод (`vehicles/wheels.ts`)

**Геометрия (узлы тела).** На каждый угол `buildVehicleBody` добавляет три
узла-опоры кузова (две оси нижнего рычага и верх стойки, жёстко связанные с
ближайшими узлами оболочки) и **узел ступицы** (неподрессоренная масса) на
двух жёстких балках-рычагах. Рычаги образуют шарнир вдоль оси z → ступица
ходит по дуге (одна степень свободы, реальное изменение развала). Пружина и
демпфер — не балка, а сила вдоль оси «ступица → верх стойки».

**`WheelSystem`** — хук `PhysicsWorld` (каждый сабшаг ≈ 2 кГц), без аллокаций:

1. **Стойки**: пружина с преднатягом (ровно держит статическую нагрузку на
   проектной высоте при любой жёсткости), раздельные сжатие/отбой,
   прогрессивный отбойник, ограничитель хода вниз; стабилизаторы по осям.
2. **Контакт шины**: радиальная пружина/демпфер (зависит от давления) →
   нагрузка; оси колеса = кадр кузова + поворот (Аккерман, схождение),
   спроецированные на плоскость земли; развал = статический + крен.
   Slip ratio и slip angle с порогами малой скорости (ведут себя как демпфер
   при стоянке → нет дрейфа), длина релаксации по боковому уводу.
   Pacejka с чувствительностью к нагрузке, эллипсом трения, развалом,
   давлением (`physics/vehicle/tyre.ts`).
3. **Привод** (`physics/vehicle/driveline.ts`) — неявный решатель:
   колесо линеаризовано `R·Fx(ω') ≈ R·Fx₀ + k(ω'−ω)` → безусловно устойчиво при
   любой жёсткости шины. Дифференциал — обобщённый «с долями момента»
   (`ω_carrier = Σ sᵢωᵢ`): одна модель для RWD/FWD/AWD (параметр
   «момент на перед»). Сцепление: сначала решается как **замкнутое** (двигатель
   и колёса — одно тело через передаточное), если нужный момент > ёмкости —
   **проскальзывание** с моментом ±ёмкость. Блокировка дифференциала — неявная
   вязкая связь левого/правого колеса (∞ = заблокирован). Тормоза/ручник —
   кулоново трение к нулю без смены знака.
4. Финальные силы шины при новых ω → на узлы ступиц (Fz по нормали, Fx, Fy).
5. Аэродинамическое сопротивление `½ρ·CdA·v²` распределено по массе.

**Двигатель** (`physics/vehicle/engine.ts`) — машина состояний
«работает ↔ заглох»: ниже `stallRpm` сгорание не держится и двигатель
глохнет; запуск стартером (I) с собственной кривой момента и временем
прокрутки до схватывания (`crankTime`), «с толкача» выше `pushStartRpm`.
Глушат двигатель не правила, а физика неявного привода: замкнутое сцепление
связывает маховик с инерцией машины, и обороты проваливаются, если бросить
сцепление на холостых, трогаться на высокой передаче или затормозить на
передаче.

**Силовой агрегат — конвейер модулей** (`physics/vehicle/powerplant.ts`).
Момент сгорания считает `EnginePipeline`: цепочка модулей по стадиям

```
intake  (дроссель → наполнение впуска с запаздыванием; turbo → наддув)
fuel    (смесь λ → КПД сгорания; топливо на сбросе — «burble»)
ignition(угол → момент ↔ тепло в выхлоп)
→ сгорание: M = карта(rpm) · наполнение·(1+наддув) · КПД(λ) · КПД(угол)
exhaust (температура газов, запас несгоревшего топлива → отстрелы, дым)
```

* Модули — данные в `VehicleDef.powerplant`, создаются через реестр
  `registerEngineModule(kind, factory)`. Набор видов — интерфейс
  `EngineModuleKinds`, который мод расширяет declaration merging'ом: новый узел
  (компрессор, закись…) подключается без правки ядра и без `any`/кастов (см.
  тест с модулем «nitrous»).
* Параметры тюнинга `<moduleId>.<key>` (`turbo.boost`, `fuel.lambda`,
  `ignition.timing`, …) маршрутизируются в `module.set(key, v)` автоматически;
  `<id>.enabled` включает/выключает модуль на лету.
* **Турбина**: обороты вала интегрируют энергию выхлопа против
  аэросопротивления, наддув ∝ ω² до порога вестгейта, размер = потенциал ×
  яма (инерция ∝ размер²); сброс газа с наддувом → блоу-офф (или помпаж
  без него); антилаг — топливо + поздний угол на сбросе.
* **Отстрелы** — не таймер: несгоревшее топливо (богатая смесь, burble,
  сильно поздний угол) копится в горячем выхлопе и вспыхивает с
  вероятностью ∝ запасу × нагреву (детерминированный ГСЧ). Бедная смесь —
  горячо и слабо; богатая — сажа.
* События (отстрелы, блоу-офф) — **монотонные счётчики** в f64-заголовке
  снапшота: главный поток сравнивает их с прошлым значением, ничего не
  теряется между кадрами и не нужны сообщения.

**Устойчивость контакта шины.** У стоящего колеса сила шины работает как
жёсткий демпфер на узле ступицы (c ≈ B·C·μ·Fz / v₀), а мягкое тело
интегрируется явно (устойчиво при c·h/m < 2). Порог малой скорости v₀
поднимается на каждом сабшаге так, чтобы c·h/m_ступицы ≤ 0.5 при любой
нагрузке и массе ступицы — без подстройки под конкретную машину.

**Шина в неявном колесе** линеаризуется по **локальному наклону** кривой
dFx/dκ (численная производная в текущей точке), а не по пиковому: до пика —
устойчиво, за пиком тормоз/ручник блокируют колесо, мощность срывает в
пробуксовку (без «скрытого ABS»).

**Коробка — выбор игрока** (меню / пауза / параметр `gear.auto`):

* **Автомат** — проскальзывающая муфта (как гидротрансформатор):
  подхватывает момент при росте оборотов, отпускает у холостых → заглохнуть
  нельзя; автопереключение (порог от газа, кулдаун, без перекрутки при
  понижении), отсечка газа на время переключения, задний ход удержанием
  тормоза на месте.
* **Механика** — между двигателем и колёсами только педаль сцепления
  (Shift): аналоговая, выжимается быстро, отпускается плавно (~0.9 с), с
  точкой схватывания (`clutchEngagement`). Передачи (Q/E, последовательно)
  включаются только при выжатом сцеплении — иначе скрежет и отказ;
  нейтраль — всегда; задний — только почти на месте. Без отсечки газа.

**`Vehicle.preStep`** (раз в шаг 120 Гц) переводит органы управления в вход
шасси: сцепление, газ/тормоз, стартер, углы руля по колёсам, тормозные
моменты (сила, баланс, ручник).

Все параметры `VehicleDef.params` (подвеска, геометрия, трансмиссия,
двигатель, шины, тормоза, жёсткость кузова) применяются **на лету** и
пересылаются в воркер.

**Замеры** (`vehicles/dynamics.test.ts`, эталонный седан 1350 кг): 0–100 км/ч
≈ 7.1 с, торможение 100–0 ≈ 39 м (без ABS), скидпад ≈ 0.94 g, курс на прямой
и при торможении стабилен, на месте без дрейфа, задний ход, механика,
передний привод, ручник, влияние пружин на крен.

### 4.4 Симуляция и потоки (`sim/`)

* `Simulation` — мир + машина + последние `DriverControls`; `step()`,
  `apply(cmd)`. Без DOM: один и тот же код работает inline и в воркере.
* `PhysicsHost` — единственный вход главного потока в физику:
  * `InlineHost` — `Simulation` на главном потоке, шагается ядром (тесты,
    снапшоты, фолбэк, `?physics=inline`). Ноль копий.
  * `WorkerHost` — `Simulation` в `physics.worker.ts` (`SimServer`).
    На главном потоке строится **shadow-машина** тем же детерминированным
    билдером (та же топология и порядок узлов); `sync()` копирует в неё
    снапшот. Рендер, камеры, HUD и тюнинг работают с `host.vehicle` одинаково
    в обоих режимах. Правки тюнинга в shadow `ParamStore` пересылаются в
    воркер командой `param`.
* **Транспорты**
  * `shared` (страница cross-origin isolated — COOP/COEP в `vite.config.ts`):
    один `SharedArrayBuffer` = Int32-ячейки управления + 3 слота снапшота.
    Неблокирующий **тройной буфер** (`tripleBuffer.ts`): писатель и читатель
    владеют разными слотами, обмен — одним `Atomics.exchange`; разрывов
    данных нет, никто никого не ждёт. Управление — второй маленький SAB
    (последние значения педалей/руля, без сообщений).
  * `transfer` (без изоляции, например хостинг без заголовков): пул из 3
    `ArrayBuffer`, передаются через `postMessage` с transfer и возвращаются
    после чтения. Управление — сообщением только при изменении.
* **Часы воркера**: аккумулятор по абсолютному времени
  (`performance.timeOrigin + now()`, сравнимо между потоками), точный сон
  `Atomics.wait` (главный поток будит `Atomics.notify` при командах), затем
  уступка event loop через `MessageChannel` (без 4-мс зажима `setTimeout`).
  В `transfer`-режиме — обычный таймер.
* **Протокол** (`protocol.ts`): `init / controls / cmd / pause / timeScale /
  step / return / dispose` → `ready / state / stepped / impact / error`.
  `Endpoint` абстрагирует Worker/MessagePort — тесты гоняют сервер в том же
  процессе через `MessageChannel` с ручными часами (`clock: 'manual'`).
* **Снапшот** (`snapshot.ts`): f64-заголовок (seq, время, simTime), f32
  телеметрия + `BodyFrame`, f32 `pos` и `prevPos`, u8 флаги балок (разрывы).
  Вьюхи создаются один раз на слот — чтение без аллокаций.
* Воркер не стартовал за 5 с или упал → автоматический фолбэк на `InlineHost`.

### 4.5 Мир и карты (`world/`)

**Карта — данные** (`MapDef`, сериализуется в JSON, `parseMap`): размер,
шаг сетки, базовая поверхность, список **фич рельефа**, статические объекты,
точки появления. `buildWorld(map)` компилирует её:

```
MapDef ─► Heightfield (высоты + id поверхности в узлах сетки)
       ─► BoxColliders (повёрнутые боксы + сетка широкой фазы)
       ─► spawns
```

* **Фичи** применяются по порядку: `hill` (холм/яма), `ramp` (подъём/
  трамплин/«стол» с площадкой и спуском), `bumps` (стиральная доска),
  `noise` (фрактальный шум в области), `road` (дорога по ломаной: красит
  поверхность и выравнивает поперечный профиль), `paint` (покраска области),
  `level` (площадка/плато с плавным краем). Виды — реестр
  `registerFeature`, набор расширяется declaration merging'ом
  `TerrainFeatureKinds` (см. тест с фичей «кратер»).
* **Поверхности** (`surfaces.ts`, реестр): трение, доп. сопротивление
  качению, «жёсткость» шины (рыхлый грунт → мягкая пологая кривая проскальзывания),
  цвет, пыль, визг. Асфальт, бетон, гравий, грунт, трава, песок, грязь, лёд.
* `Heightfield` реализует `Ground`: билинейная высота + аналитический градиент
  → нормаль, свойства поверхности из таблиц. Поэтому **узлы кузова и шины
  работают на склонах и разных грунтах без единого частного случая**.
* **Препятствия** (`colliders.ts`): узел ↔ бокс — выталкивание через грань
  наименьшего проникновения, restitution, кулоново трение (как у земли),
  материалы (бетон, дерево, металл, шины — упругие). Солвер получает их через
  интерфейс `StaticColliders` из слоя физики (физика не знает о `world/`).
  Солвер отдаёт максимальную скорость удара за шаг → события ударов (звук).
* Мир детерминирован → строится независимо в воркере и на главном потоке
  (кэш `worldFor`), рендер берёт ту же скомпилированную карту.

**Как сделать карту:** скопировать `world/maps/proving.ts`, собрать из фич,
добавить объекты и точки, `registerMap(def)` (или JSON через `parseMap`).
Проверка: `npm run snap -- --map=<id> --views=map` (вид всей карты сверху),
`--spawn=<id> --views=iso,chase` — любая точка; тесты `world/world.test.ts`
проверяют, что все карты строятся.

### 4.6 Разрушаемость

* **Зоны прочности кузова**: `BodyStation.strength` (по умолчанию выводится:
  концы — сминаемые 0.5, сечения с крышей — каркас салона 1.6). Балка прочна
  как более слабое из двух сечений (жёсткость и предел текучести).
* **Удары** о препятствия и землю деформируют кузов через балки (пластика,
  разрывы). Замеры (`sim/world.dynamics.test.ts`): лоб в стену 60 км/ч —
  смята передняя зона, салон < 10 % её деформации; 25 км/ч — двигатель цел,
  100 км/ч — разбит.
* **Двигатель**: «здоровье» из пластической деформации моторного отсека
  (балки впереди передней оси) → момент × здоровье, ниже порога — не
  работает и не заводится (`DEAD_HEALTH`).
* **Отрыв колеса**: оба нижних рычага порваны → стойка не держит, привод и
  тормоз на колесо не идут, ступица — свободный узел (колесо отлетает).
* **Погнутая подвеска уводит машину**: направление колеса берётся из
  фактической оси шарнира рычагов (а не из «идеального» кадра).
* **Рваные панели**: треугольник обшивки, растянутый > 1.6× проектного ребра,
  схлопывается — дыры там, где порвались балки.
* Ремонт — `R` (сброс) или телепорт к точке карты (пауза → «Точки карты»).

## 5. Ядро (`core/`)

* `Kernel<Events>` — токены сервисов (`token<T>(id)`), `provide/get/tryGet`,
  системы с `order`, `use(...plugins)` с проверкой `requires`, `dispose` в
  обратном порядке.
* `EventBus<Map>` — строго типизированные события (`GameEvents` в
  `app/tokens.ts`).
* `FixedStepLoop` — фиксированный шаг, пауза, timeScale, защита от «спирали
  смерти», статистика.
* `ParamStore` — схема параметров, clamp, подписка, JSON-сериализация пресетов.
* `Rng`, `math/scalar`, `math/vec3`.

### Как добавить плагин

```ts
export const myPlugin = (): Plugin<GameEvents> => ({
  id: 'my',
  requires: ['vehicle'],
  setup(ctx) {
    const v = ctx.get(T.vehicle)
    ctx.addSystem({ id: 'my', order: 35, fixedUpdate(dt) { /* ... */ } })
  },
})
// createGame({ ..., extraPlugins: [myPlugin()] })
```

### Как добавить машину

1. Определение через `defineVehicle({...})` (`src/vehicles/catalog.ts` —
   примеры): сечения кузова, материал, колёса, двигатель + модули силового
   агрегата, КПП, шины, голос двигателя (`sound`), патрубки выхлопа.
   Подвеску удобно задавать физически: `corner(масса, доля оси,
   неподрессоренная, частота Гц, ζ)` → жёсткость `k = m(2πf)²`,
   демпфер `c = 2ζ√(km)`.
2. Параметры тюнинга генерируются сами (`standardParams`): заводские
   значения машины, диапазоны вокруг них, параметры модулей — только для
   имеющихся модулей.
3. `registerVehicle(def)` (или добавить в `registry.ts`).
4. `src/vehicles/catalog.test.ts` автоматически проверит новую машину:
   масса, валидный скин, **триангулированность креплений подвески**
   (`attachmentSpread` — направления балок охватывают все 3 оси),
   **численную устойчивость** (ω·h каждого узла < 1.3 при пределе 2),
   стоянку без дрейфа на проектной высоте, разгон/торможение, все параметры
   тюнинга на min/max.
5. `npm run snap -- --vehicle=<id>` — проверить все проекции глазами.

**Каталог** (все — оригинальные): Kuzov K1 (седан, задний, R6),
Piccolo (хэтч, передний, R4), Strela (купе, задний, турбо R6),
Burlak (пикап, полный, V8), Vikhr (ралли-хэтч, полный, турбо R4 + антилаг).

## 6. Рендер (`render/`)

* `RenderService` — WebGLRenderer (ACES, PCF soft shadows, pixel ratio ≤ 2),
  сцена, камера. В snapshot-режиме — фиксированный размер и
  `preserveDrawingBuffer`.
* `environment.ts` — небо, туман, полусферный свет + солнце с тенью,
  следящей за машиной, процедурная текстура земли (canvas, без файлов).
* `skin.ts` — чистая генерация треугольной «кожи» поверх решётки: каждая
  вершина привязана к узлу физики (`nodeOfVertex`), группы материалов (краска,
  стекло, днище, салон), ориентация граней наружу/внутрь проверяется
  автоматически.
* `VehicleView` — копирует интерполированные позиции узлов в
  `DynamicDrawUsage`-буфер, flat-нормали, колёса по `BodyFrame`,
  оверлей балок (F3).
* **Эффекты** (`render/particles.ts`, `render/effects.ts`): пулы частиц на
  GPU-инстансинге (камерные квады, мягкий спрайт в шейдере), симуляция в SoA
  typed arrays, swap-remove → живые частицы непрерывны, один draw call на
  пул, загрузка только живого диапазона; 2 пула — дым (normal) и пламя
  (additive). `VehicleEffects` читает только синхронизированную машину и
  телеметрию: дым шин ∝ скорость скольжения пятна × нагрузка, дым выхлопа
  (цвет от сажи/смеси), отстрелы → вспышка пламени + клуб дыма + точечный
  свет. Эмиссия по времени с переносом дробной части (не зависит от FPS).
  В snapshot-режиме `drive()` шагает частицы вместе с физикой.
* `CameraRig` — чистая математика поз камеры: `chase` (сзади, сглаженный
  курс), `cockpit` (глаз водителя, от первого лица; мышь — обзор, колесо — FOV,
  двойной клик — вперёд), `top` (сверху, «вперёд» всегда вверх экрана; колесо —
  высота), `free` (свободная: вращение мышью в любую сторону вокруг машины,
  колесо — зум, камера не уходит под землю; перетаскивание в chase/top
  переключает в free). Мышь подключает `bindCameraPointer` (pointer capture,
  wheel с `passive: false`). `snapPose` — детерминированные проекции
  `front/back/left/right/top/iso/iso-rear/cockpit/chase`.

## 7. Звук (`audio/`)

```
AudioWorklet 'kuzov-engine' ─┐
impact (noise burst) ────────┼─► bus ─► compressor ─► master ─► out
(шаг 5: шины, ветер, турбо) ─┘
```

* `dsp/engineSynth.ts` — `EngineVoice`: фаза коленвала (2 оборота на цикл),
  N вспышек цилиндров с индивидуальной неравномерностью, импульсы → банк
  резонансов выхлопа (band-pass) + шум впуска по нагрузке → DC-фильтр →
  мягкое насыщение. Частота вспышек `rpm/60 · cyl/2` проверяется тестом через
  автокорреляцию.
* `engine.worklet.ts` — тонкая обёртка `AudioWorkletProcessor`
  (k-rate параметры rpm/load/throttle). Vite собирает её отдельным чанком
  (`?worker&url`).
* Одноразовые звуки (`dsp/oneshots.ts`): хлопок выхлопа, «пшик» блоу-офф,
  помпаж — рендерятся кодом один раз в буферы (детерминированно, с тестами).
  Свист турбины (осциллятор, высота ∝ обороты вала), визг шин (резонансный
  шум ∝ скольжению).
* `AudioService` — интерфейс; `WebAudio` (ленивая инициализация по жесту
  пользователя) и `NullAudio` (тесты).

## 8. Ввод (`input/`)

`InputMapper` без DOM: коды клавиш → действия (`Bindings` — данные),
сглаживание педалей, руль с возвратом и уменьшением угла от скорости,
edge-triggered действия (`consume`). Плагин `inputPlugin` подключает его к
`window`. Геймпад/руль (шаг 10) пишут в те же `DriverControls`.

## 9. UI (`ui/`)

* Preact + `@preact/signals`. `store.ts` — единственный мост: события ядра →
  signals, телеметрия семплируется 15 Гц.
* `kit/` — собственный UI-кит (`Button`, `Slider`, `Toggle`, `Tabs`, `Panel`,
  `Stat`, `Kbd`, `Gauge`), `icons/` — собственные SVG-иконки (path-данные).
* `screens/` — `MainMenu`, `Hud`, `TuningPanel` (генерируется из
  `ParamDef[]`), `PauseMenu`.
* Стили — CSS с токенами (`styles/tokens.css`), вложенность и
  `@custom-media` компилирует Lightning CSS. См. `STYLE.md`.

## 10. Визуальное тестирование (`devtools/`)

Snapshot-режим: `/?snap&vehicle=k1-sedan&view=iso&t=1.5&w=1280&h=720&beams=1`

* Без rAF, ввода и звука; симулирует `t` секунд, рендерит один кадр, ставит
  `<html data-snap="ready">`.
* `window.__kuzov`: `setView(view)`, `simulate(s)`, `setBeams(on)`,
  `kick(node, vx, vy, vz)` (удар для тестов деформации), `render()`,
  `info()`, `debug()`.
* `npm run snap` — Playwright + SwiftShader, PNG в `snapshots/`:

```
npm run snap                                         # все проекции
npm run snap -- --views=iso,top,cockpit --beams      # с каркасом балок
npm run snap -- --kick=0,0,0,-15 --after=1           # удар по узлу 0, затем снимок
npm run snap -- --w=1920 --h=1080 --t=3
npm run snap -- --views=front,iso --drive=throttle:0.5,steer:0.7 --drive-t=2.5 --tag=turn
npm run snap -- --views=back --param=fuel.lambda:0.72,fuel.overrun:1,turbo.enabled:1 \
                --drive=throttle:1@4 --drive=throttle:0@0.35 --tag=pops   # цепочка шагов
npm run snap -- --map=proving --views=map                                 # вся карта сверху
npm run snap -- --map=proving --spawn=crash --launch=70 --drive=brake:0@1.4 --beams  # краш-тест
```

`--drive` держит органы управления заданное время (`__kuzov.drive(c, s)`) —
так проверяются крен, поворот колёс, посадка при разгоне/торможении.

* `npm run e2e` — прогон реального UI (меню → газ → камеры → F3 → тюнинг →
  пауза), скриншоты `snapshots/ui-*.png`, падает на любой ошибке страницы.
  Проверяет по оверлею F3 режим физики и что она делает ≥ 60 шагов/с.
  Флаги: `--preview` (релизная сборка), `--physics=inline`,
  `--no-isolation` (без COOP/COEP → транспорт `transfer`).

## 11. Тестирование

| Уровень | Инструмент | Что |
|---|---|---|
| Unit | Vitest (node) | ядро, солвер, двигатель, КПП, шины, решётка, скин, камеры, ввод, DSP |
| Потоки | Vitest + MessageChannel | тройной буфер (случайные чередования), снапшот, WorkerHost ≡ InlineHost для обоих транспортов, команды, удары |
| Компоненты | Vitest + happy-dom | UI-кит, генерация панели тюнинга |
| Perf | `npm run perf` | бюджет физики (машина < 10 % шага 120 Гц), стоимость `sync()` главного потока |
| Визуальные | `npm run snap` | любая машина × любая проекция |
| E2E | `npm run e2e` | реальный UI в Chromium, dev и prod |

Физические тесты проверяют законы, а не числа из головы: свободное падение
`g·t²/2`, устойчивый покой на земле, пластика и разрыв при ударе,
детерминизм, частота вспышек двигателя.

## 13. Производительность — правила

* Горячие циклы: typed arrays, индексная арифметика вручную, `!` вместо
  проверок (разрешено, т. к. индексы гарантированы построением).
* Никаких аллокаций за кадр/шаг (векторы-временные — модульные константы).
* UI не перерисовывается чаще 15 Гц; HUD без `backdrop-filter`.
* Один меш на кузов, группы материалов отсортированы → минимум draw calls.
* Бюджеты: физика одной машины < 0.83 мс на шаг 120 Гц (сейчас ≈ 0.28 мс с
  колёсами и приводом, и она в отдельном потоке), `WorkerHost.sync` на главном потоке < 20 мкс
  (сейчас ≈ 0.1 мкс без новых данных), кадр < 8 мс на средней GPU.
* Деплой: для `shared`-транспорта хостинг должен отдавать
  `Cross-Origin-Opener-Policy: same-origin` и
  `Cross-Origin-Embedder-Policy: require-corp`; без них игра работает через
  `transfer`.
